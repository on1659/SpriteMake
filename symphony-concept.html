Codex orchestration pattern

Symphony는 에이전트를 직접 조종하는 방식에서, 작업 보드가 에이전트를 지휘하는 방식으로 바꾸는 개념이다.

핵심은 “Codex 세션을 몇 개 켜서 사람이 계속 운전한다”가 아니라, “이슈, 티켓, batch 같은 작업 단위를 중심에 두고 각 작업마다 격리된 에이전트 실행 환경을 붙인다”는 전환이다.

한 문장 정의

Symphony는 “에이전트 하나”가 아니라, 여러 Codex 실행을 작업 단위로 계속 돌리는 운영 방식이다.

Control plane

이슈 트래커가 지휘부가 된다

Linear나 GitHub Issue 같은 작업 보드가 “무슨 일이 열려 있고, 무엇이 막혔고, 무엇이 리뷰 대기인지”를 결정한다. 사람은 세션 목록을 기억하지 않고 티켓 상태를 본다.

Always-on

열린 작업마다 에이전트가 붙는다

활성 상태의 작업은 전담 workspace와 agent run을 얻는다. 실행이 멈추거나 실패하면 orchestrator가 재시도하거나 정리한다.

Policy

규칙은 repo 안에 둔다

팀의 작업 규칙, 검증 방식, handoff 조건은 WORKFLOW.md 같은 문서에 둔다. 에이전트가 매번 같은 기준으로 움직이게 만드는 장치다.

Human role

사람은 운전자가 아니라 리뷰어다

사람이 매 스텝을 조종하는 대신, 결과물, PR, QA 로그, 리뷰 패킷을 확인한다. 관심은 “세션 관리”에서 “작업 품질 관리”로 옮겨간다.

기존 Codex와 Symphony의 차이

둘 다 Codex를 쓰지만, 사람이 붙잡고 있는 대상이 다르다.

Interactive agent

기존 방식: 세션 중심

사람이 Codex 세션을 열고, 지시하고, 로그를 보고, 중간에 방향을 바꾸고, 멈췄는지 직접 확인한다. 작은 작업에는 빠르지만 여러 세션을 동시에 굴리면 기억해야 할 맥락이 급격히 늘어난다.

  1. 1사람이 터미널이나 웹에서 Codex 세션을 시작한다.
  2. 2작업 설명을 직접 입력하고, 진행 중에 계속 확인한다.
  3. 3실패하거나 헷갈리면 사람이 다시 지시한다.
  4. 4결과를 모아 PR, 문서, QA 상태를 사람이 정리한다.
Symphony pattern

Symphony 방식: 작업 중심

사람이 티켓을 만들면 orchestrator가 적격 작업을 찾아 workspace를 만들고 agent를 실행한다. 사람은 작업 보드와 리뷰 결과를 보고 개입한다.

  1. 1사람이 Linear/GitHub Issue/SpriteMake batch 같은 작업 단위를 만든다.
  2. 2orchestrator가 상태를 읽고 실행 가능한 작업을 고른다.
  3. 3작업별 workspace에서 Codex가 구현, 조사, 검증, 보고를 수행한다.
  4. 4사람은 Human Review 상태의 결과물만 깊게 본다.

구조를 그림으로 보면

Symphony는 화려한 UI 이름이 아니라, tracker, workspace, agent runner, workflow policy를 묶는 얇은 운영 계층이다.

Issue Tracker

작업의 원천. 상태, 우선순위, block 관계, 담당 범위를 담는다.

Linear / GitHub Issues / output queue

Symphony Orchestrator

주기적으로 tracker를 읽고, 작업 실행/중단/재시도/정리를 판단한다.

poll, dispatch, retry, reconcile

Workspace + Agent

작업별 격리 폴더에서 Codex가 repo 규칙을 읽고 실제 일을 한다.

WORKFLOW.md + Codex run
Workflow Loader

작업 규칙 로딩

WORKFLOW.md의 front matter와 prompt body를 읽어 agent 실행 지침으로 바꾼다.

Workspace Manager

격리 환경 생성

이슈 ID를 workspace path에 매핑하고, 작업별 파일 시스템 영역을 준비한다.

Agent Runner

Codex 실행

작업 내용과 workflow prompt를 합쳐 Codex app-server client 또는 agent 실행을 시작한다.

Observability

상태 관측

여러 agent가 동시에 돌 때 로그, 상태, retry 정보를 사람이 볼 수 있어야 한다.

작업 하나가 흘러가는 과정

아래 버튼을 눌러 각 단계에서 누가 무엇을 하는지 확인할 수 있다.

SpriteMake에 적용하면 무엇이 좋아지나

여기서는 거대한 Symphony 서버보다, output 폴더와 markdown 상태를 작업 큐처럼 쓰는 mini-Symphony가 현실적이다.

Request refinement

대충 말한 요청을 제작용 브리프로 정제

“드래곤 스프라이트 만들어줘”를 strict atlas, variant, anchor, Y-axis baseline, QA 조건이 포함된 생성 요청으로 바꾼다.

  • 원문 요청 보존
  • 누락된 runtime 조건 기본값 보강
  • gpt-image-2 copy-ready prompt 생성
Batch state machine

output batch를 상태 머신으로 관리

각 batch 폴더가 티켓처럼 동작한다. 폴더 안의 MD와 manifest, QA 상태를 보고 다음 액션을 자동으로 정한다.

  • REQUESTS.md가 비면 refine 필요
  • generated/에 PNG가 생기면 QA 필요
  • QA 통과 전에는 final/ 금지
Review packet

사람이 볼 결과만 모아주기

모든 중간 로그를 사람이 붙잡는 대신, 마지막에 검토해야 할 프롬프트, manifest, bbox, preview tool 경로를 묶어준다.

  • 프롬프트 원문과 보강 이유
  • alpha bbox / per-cell bbox 요약
  • 게임 프로젝트로 이동 가능 여부
Intake 자연어 요청 저장, batch 폴더 생성
Refine brief, target path, atlas contract 보강
Prompt Ready gpt-image-2용 copy-ready prompt 준비
Generated 외부 생성 PNG를 generated/에 배치
QA size, grid, anchor, baseline, bbox 검사
Final Candidate QA 통과 후 게임 integration 후보로 표시 
Example mini-Symphony rule for SpriteMake

IF output/*/PROMPT.md exists
AND REQUESTS.md has missing runtime fields
THEN run request refinement

IF generated/*.png appears
THEN run PNG QA and update MANIFEST.md + QA.md

IF QA passes
THEN mark as final candidate
ELSE keep in generated/ and write regeneration notes

쓸 때의 감각

Symphony의 장점은 에이전트가 똑똑해지는 것보다, 일을 담는 그릇이 에이전트 친화적으로 바뀌는 데 있다.

작업을 작게만 쪼개지 않아도 된다

이슈가 여러 PR, 조사, 하위 작업으로 번질 수 있다. 에이전트가 새 follow-up task를 제안하는 구조도 가능하다.

엄격한 state machine만으로는 부족하다

OpenAI 글에서도 에이전트를 너무 딱딱한 노드로만 보면 한계가 있었다고 말한다. 목표와 도구를 주고, 좋은 handoff 기준을 세우는 쪽이 더 중요하다.

격리는 필수다

작업별 workspace가 있어야 여러 agent run이 서로 파일을 덮어쓰거나 상태를 혼동하지 않는다.

모든 작업에 맞는 건 아니다

강한 제품 판단, 모호한 탐색, 즉석 대화가 중요한 작업은 여전히 사람과 interactive Codex가 같이 가는 편이 낫다.
